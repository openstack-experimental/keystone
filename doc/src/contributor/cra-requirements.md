# Cyber Resilience Act requirements

This page derives what the EU Cyber Resilience Act (CRA, Regulation (EU)
2024/2847) asks of Keystone and compares how the Python implementation and this
Rust implementation currently answer it. It is an engineering gap analysis, not
legal advice, and it is not a conformity claim.

How to read the evidence:

- **Rust** statements are verified against this repository and cite a file.
- **Python** statements describe upstream OpenStack Keystone from general
  knowledge of that project. They are **not verified in this repository** and
  must be re-checked against the release being compared before they are quoted
  in any compliance document. Rows where this matters are marked _(unverified)_.

Related pages: [Security model](security-model.md),
[Security architecture review](security-review.md),
[Crypto inventory](crypto-inventory.md),
[Python API compatibility](python-compatibility.md).

## 1. Applicability

### Timeline

| Date        | What applies                                                                       |
| ----------- | ---------------------------------------------------------------------------------- |
| 10 Dec 2024 | Regulation in force                                                                |
| 11 Sep 2026 | Reporting duties of Art. 14 (actively exploited vulnerabilities, severe incidents) |
| 11 Dec 2027 | All remaining obligations (Annex I, Art. 13, conformity assessment, CE marking)    |

The 10 Dec 2024 and 11 Sep 2026 dates have already passed. Reporting duties
therefore bind a manufacturer today for products placed on the market, including
products placed before 11 Dec 2027.

### Who is the "manufacturer"

The CRA binds economic operators that make a product with digital elements
available **in the course of a commercial activity**. The role decides the
workload, and it is not the same for the two implementations:

| Actor                                                                         | Role                                                                                 | Consequence                                                                                                         |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| Distribution vendors and service providers that ship or sell a Keystone build | Manufacturer (Art. 13)                                                               | Full Annex I, II, VII duties, CE marking. They inherit upstream gaps and must close them.                           |
| The upstream project, if no commercial activity                               | Out of scope (recital 18), or **open-source software steward** (Art. 3(14), Art. 24) | Light regime: a documented cybersecurity policy, cooperation with market surveillance, and vulnerability reporting. |
| Operators running Keystone as a service for their own cloud                   | Not the CRA manufacturer, but covered by NIS2 if essential/important                 | Need the manufacturer's evidence (SBOM, advisories, support period).                                                |

Both implementations are, for a vendor, "software, placed on the market
separately". Whether this repository's maintainers are a steward or merely a
supplier of components is a governance decision (recorded in the
[cybersecurity policy](cybersecurity-policy.md): steward). The rest of this page
assumes a vendor-grade bar, because that is the bar a downstream manufacturer
needs the project to meet.

### Product class

Keystone is an identity and access management system. Annex III class I lists
"identity management systems and privileged access management software". Treat
Keystone as a **class I important product** until a vendor's assessor says
otherwise. Verify against the Commission's implementing act on the technical
description of the Annex III categories. In class I a manufacturer may use
internal control (module A) only if it applies a harmonised standard or an EU
cybersecurity certification scheme in full. Otherwise it needs third-party
assessment (modules B+C or H). Harmonised standards were still in preparation at
the time of writing. Plan for the third-party path. The class is confirmed; the route is the
manufacturer's decision (see the [technical file index](cra-technical-file.md)).

The default (non-important) class does not change the technical requirements
below; it changes who signs off.

which breaks operator access to the admin Unix socket (`curl --unix-socket` from
inside the pod, whose peer-credential check rules out a differently privileged
debug container) and the shell-based entrypoints in the reference manifests. The
images stay on `debian:trixie-slim`, digest-pinned.

## 5. Python and Rust compared

| Dimension                   | Python Keystone _(unverified)_                                | This repository                                                                                                    | Net for CRA                                                                                  |
| --------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Memory-safety class of bugs | Eliminated in Python code; present in C extensions            | Eliminated in workspace code (`unsafe_code = forbid`); dependencies may use `unsafe`                               | Rust slightly ahead, but not a CRA test                                                      |
| Dependency pinning          | Version ranges plus upper constraints                         | `Cargo.lock` committed, `cargo-auditable` in release builds                                                        | Rust ahead                                                                                   |
| Dependency policy gates     | Constraints review                                            | `cargo deny` (advisories, licences, bans, sources), `cargo vet`, Dependabot                                        | Rust ahead; fix `unknown-*` warn levels                                                      |
| SBOM                        | Not published                                                 | Embedded in binary, not published                                                                                  | Both need work                                                                               |
| Release provenance          | Signed tags/tarballs                                          | Build attestations, container attestations, cosign for policy                                                      | Rust ahead if consumer docs are added                                                        |
| Authorization testing       | Policy YAML; unit tests                                       | OPA bundle, Rego tests, handler↔policy contract checks, mutation and property tests                                | Rust ahead                                                                                   |
| Fuzzing                     | None known                                                    | Five targets, weekly                                                                                               | Rust ahead                                                                                   |
| Audit trail                 | pyCADF middleware, `oslo.log`                                 | Native CADF, HMAC-signed, spool, syslog                                                                            | Rust ahead                                                                                   |
| Cryptographic documentation | Not centralised                                               | Full inventory with FIPS status                                                                                    | Rust ahead                                                                                   |
| FIPS posture                | Depends on host OpenSSL                                       | AWS-LC `fips` build for storage, audit and TLS; many primitives still not validated (Fernet, JWS, password hashes) | Rust has a path; neither is fully validated                                                  |
| Vulnerability disclosure    | Mature, public, with advisories and CVEs                      | GitHub private reporting, advisories and a documented process                                                      | **Python ahead**                                                                             |
| Support policy              | Defined stable branches and EOL                               | None (0.1.x)                                                                                                       | **Python ahead**                                                                             |
| Compatibility surface       | Complete v3 API                                               | Subset of v3 plus v4 (`python-compatibility.md`)                                                                   | Rust must keep the Python gap list current: missing endpoints are a functional, not CRA, gap |
| Interop obligations         | n/a                                                           | Fernet, bcrypt, scrypt, AWS SigV2 and TOTP-SHA1 are Compat-fixed                                                   | Weak primitives are inherited; document the rationale as risk acceptance                     |
| Container hardening         | Reference image is test-only (`tools/Dockerfile.py-keystone`) | Image runs as root by default                                                                                      | Gap in both; fix Rust image                                                                  |

Key point for a mixed deployment: the CRA applies per product. When both
services run side by side behind one proxy (see
[installation](../install/index.md)), each needs its own SBOM, advisory feed and
support period, and the shared Fernet and credential keys are in the scope of
both risk assessments.

## 6. Work items

Priorities: **P0** blocks any downstream manufacturer today (reporting duties
apply since 11 Sep 2026); **P1** needed before 11 Dec 2027; **P2** hardening.

No open work items. The project-side gaps found in this analysis are closed or
recorded as accepted risks in the [cybersecurity policy](cybersecurity-policy.md),
[VEX statements](vex.md) and [support policy](support-policy.md). Remaining
duties belong to the manufacturer; see the
[technical file index](cra-technical-file.md).

  whenever this page is cited externally.

- When a work item lands, change its row here and, if it affects cryptography,
  the [crypto inventory](crypto-inventory.md) in the same change.

  are stated here but not yet verified against the Official Journal text.
